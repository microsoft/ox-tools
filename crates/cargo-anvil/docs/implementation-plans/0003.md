# Implementation Plan 0003 — Declarative container configuration

This plan implements the design in
[container-config.md](../design/container-config.md): the public
`.anvil/config.toml` contract for consumer image extensions, managed cache
volumes, explicit host mounts, and registered repository commands.

Companion docs:
- [container-config.md](../design/container-config.md) — the contract itself:
  trust model, schema, validation, image identity and coherence, ordering, and
  catalog specialization.
- [containers.md](../design/containers.md) — container execution, the existing
  `customize.*` seam, and the image-identity split this plan extends.
- [extensibility.md](../design/extensibility.md) — the catalog artifact API
  used to render and specialize the `Containerfile`.

The design is landing as documentation first, per the convention established by
[0002.md](./0002.md). This plan is the code work that makes the implementation
match it. No user-facing surface is invented here beyond what the design
describes.

---

## Sequencing principles

1. **Parse and validate before anything is rendered.** The whole schema can be
   parsed, validated, and unit-tested with zero change to emitted output. A
   repository without `.anvil/config.toml` must produce byte-identical output
   through **every** commit in this plan — a snapshot diff is a bug, not
   expected churn
   ([§7.3](../design/container-config.md#73-repositories-that-declare-nothing)).
2. **Close the existing build-context hole before adding to it.** The ignore
   file currently un-ignores `.anvil/container/*` wholesale, so any new
   execution-only file would land in the image under an unchanged tag. That is
   fixed first, on its own, because it is a pre-existing correctness issue that
   this contract would otherwise amplify
   ([§7](../design/container-config.md#7-image-identity)).
3. **Make the ownership container safe before it takes declared input.**
   Converting the root `chown` from a shell string to argv is a prerequisite
   for caches, not a follow-up
   ([§9.1](../design/container-config.md#91-no-value-reaches-a-shell)).
4. **Runtime policy before image content.** Caches and mounts are additive
   runtime arguments that never change image identity, so they land first and
   prove the generated-runtime-data path end to end. Image extensions change
   identity and are sequenced after that path is trusted.
5. **Registered commands last within the shared contract.** They widen a
   capability boundary and reuse the argument machinery earlier phases
   establish, so they land as their own reviewable group.
6. **Every commit leaves the crate compiling** and the base tool behaving
   identically for repositories that declare nothing.
7. **Bash and PowerShell change together.** A driver behavior never lands on
   one host without the mirrored test on the other.

Phases 0–4 correspond to PR 3 in the work-item split (WI 7689199 + 7689201);
Phase 5 is PR 4 (WI 7689198).

## Phase 0 — Pre-existing correctness

These two commits are independently valuable and would be worth landing even if
the rest of this plan were abandoned.

### Commit 1: allowlist the build context

- `Containerfile.dockerignore` stops un-ignoring `.anvil/container/*` and
  instead names each build input explicitly, so an execution-only file cannot
  silently become image content.
- The ignore file and the `image-id.*` exclusion list are generated from one
  list in Rust, so they cannot disagree.
- Test: every file in the generated container directory is either hashed or
  ignored, asserted by iterating the generated tree rather than a hardcoded
  list, so a future artifact cannot be added without a decision.
- Design refs: [§7](../design/container-config.md#7-image-identity).

### Commit 2: argv-based ownership initialization

- Both drivers invoke the root `chown` with positional arguments instead of
  `sh -c "<string>"`, and the ownership container stops mounting the worktree
  since it only initializes volumes.
- Driver tests on both hosts assert the ownership container's argv shape and
  that the worktree bind is absent from it.
- Design refs:
  [§9.1](../design/container-config.md#91-no-value-reaches-a-shell),
  [§9.2](../design/container-config.md#92-where-declarations-apply).

## Phase 1 — The configuration model (no behavior change)

### Commit 3: schema types and parsing

- **New module** `container::config`: `ContainerConfig { image, caches, mounts,
  commands }`, with `ImageConfig { packages, env, files, steps }`,
  `CacheSpec { name, target, scope }`, `MountSpec { name, source, target, mode }`,
  `CommandSpec { name, recipe, workdir, args }`, `ArgSpec { name, kind, required }`.
- Closed enums `CacheScope { Worktree, Image, Global }`,
  `MountMode { ReadOnly, ReadWrite }`,
  `MountSource { Repository, Sibling, Host }`,
  `ArgKind { Token, Integer, Path, Enum(Vec<String>) }`.
- Parsing with the existing `toml_edit` dependency — no new crate. Unknown
  tables and keys are collected and rejected, not ignored.
- `ContainerConfig::load(repo_root) -> Result<Option<Self>, AppError>`:
  `Ok(None)` when the file is absent, so absence is a normal state rather than
  an error path.
- Unit tests: every documented key parses; unknown table, unknown key, wrong
  type, a `source` table with zero or two kinds, and malformed TOML each
  produce a diagnostic naming the offending path.
- Design refs:
  [§4, §5](../design/container-config.md#4-where-the-declaration-lives).

### Commit 4: validation

- `ContainerConfig::validate()` implementing
  [§6](../design/container-config.md#6-validation-and-diagnostics) in full:
  duplicate names; absolute normalized container targets; the reserved-target
  list checked in **both** directions (descendant and ancestor); pairwise
  target collision and nesting; worktree containment for `repository` sources,
  `path` arguments, `workdir`, and image `file` sources; the `sibling`
  single-segment rule; the restricted character set; reserved environment keys;
  required-before-optional argument order; `enum` arguments requiring `values`;
  the `anvil-`/`_anvil-` prefix ban and the recipe-name pattern.
- Path normalization is lexical, not filesystem-resolved, so validation does
  not depend on what happens to exist on the generating host. Symlink
  resolution is the drivers' job at runtime.
- Unit tests: one per rejection, asserting the diagnostic names the file, the
  table, the value, and the remedy. Table-driven over the reserved-target and
  reserved-environment lists so a future addition cannot land untested.
  Explicit cases for `/usr` (ancestor shadowing) and `/workspace/target`
  (descendant).
- Design refs: [§6](../design/container-config.md#6-validation-and-diagnostics).

### Commit 5: the coherence record

- SHA-256 helpers over normalized content, reusing `checksum.rs`. Presence is
  encoded separately from content, so a missing file and an empty file are
  distinguishable.
- A `CoherenceRecord` type carrying the presence marker, the configuration
  checksum, and the checksums of every configuration-derived artifact.
- Unit tests: identical content on CRLF and LF produces the same checksum; a
  missing file and an empty file produce different records.
- Design refs: [§7.2](../design/container-config.md#72-staleness).

## Phase 2 — Generated runtime data

### Commit 6: render `runtime.conf`

- New artifact `.anvil/container/runtime.conf`, emitted **only** when
  `.anvil/config.toml` exists, so a repository that declares nothing keeps
  today's tree byte for byte.
- Line-oriented, tab-separated, one record per declaration, with the coherence
  record written last, after every artifact it vouches for.
- Generation **fails** when a configuration-derived artifact resolves to
  `Propose` or `LeaveAlone` rather than being updated in place, so the runtime
  file can never vouch for a `Containerfile` the repository is not using.
- Tests: snapshot output unchanged without a configuration file; the file is
  present and correct with one; generation fails with an actionable diagnostic
  when the `Containerfile` is locally modified.
- Design refs: [§7.2, §7.3, §9](../design/container-config.md#72-staleness).

### Commit 7: driver coherence guard

- Both drivers verify the presence marker, the configuration checksum, and
  every derived-artifact checksum before validating prerequisites, and fail
  with the documented message.
- Bash uses the existing `sha256sum`/`shasum` selection; PowerShell uses
  `SHA256.HashData`, both already present for the image ID.
- Driver tests on both hosts: a matching record proceeds; an edited
  configuration, a modified `Containerfile`, a configuration file added without
  regeneration, and a deleted configuration file with an orphaned
  `runtime.conf` each fail before any `docker` invocation.
- Design refs: [§7.2, §7.3](../design/container-config.md#72-staleness).

## Phase 3 — Caches and mounts (WI 7689201)

### Commit 8: managed cache volumes

- Drivers read cache records, derive volume names per the
  [§5.2](../design/container-config.md#52-containercache-managed-cache-volumes)
  scope rules, create them with the documented labels, and include their
  targets in the argv-based ownership container from Commit 2.
- Driver tests on both hosts: each scope produces the documented name;
  `worktree` scope is stable across image IDs and `image` scope is not; labels
  are applied; targets appear in the ownership container and in the recipe
  container; declaring nothing still creates exactly today's three volumes.
- Design refs:
  [§5.2, §9.2](../design/container-config.md#52-containercache-managed-cache-volumes).

### Commit 9: explicit host mounts

- Drivers append mount arguments with the declared mode, resolve the three
  source kinds, and refuse to proceed when a `repository` source resolves
  outside the worktree or a `host` source is missing. The PowerShell driver
  translates sources with `wslpath`, the same call it already makes for the
  repository root.
- Mounts reach the preparation, APRZ, and recipe containers, never the root
  ownership container.
- Driver tests on both hosts: read-only is the default and is emitted
  explicitly; read-write is honored; each source kind resolves correctly; a
  symlinked `repository` source pointing outside the worktree is rejected at
  runtime; Windows path translation produces the expected WSL source.
- Design refs:
  [§5.3, §6, §9.2](../design/container-config.md#53-containermount-explicit-host-mounts).

## Phase 4 — Image extensions (WI 7689199)

### Commit 10: markers and renderer

- Add the `# anvil-container-packages:` and `# anvil-container-extensions`
  markers to the public `Containerfile` at the positions defined by
  [§11](../design/container-config.md#11-ordering).
- Renderer replaces the extension marker with `packages`, `file` copies
  (JSON-form `COPY`), `step` scripts (one `RUN` each, in declaration order),
  and quoted `ENV` declarations — or removes both markers when nothing is
  declared.
- The package command comes from the marker line, not from Rust, so a
  downstream catalog specializes it by replacing the `Containerfile` it already
  owns. `{{packages}}` is substituted with shell-quoted names.
- Errors: extensions declared with no marker present, naming the tool whose
  catalog produced the file; duplicate markers, naming the line numbers.
- Fixture tests: a sample repository renders the expected `Containerfile`; a
  marker with a different package command renders that command; a missing
  marker with declared extensions fails; duplicate markers fail. Examples use
  no Microsoft- or COSMIC-specific dependency.
- Design refs:
  [§5.1, §8, §11](../design/container-config.md#51-containerimage-image-extensions).

### Commit 11: declared files in identity and context

- Files named by `[[container.image.file]]` are added to the ignore-file
  allowlist and to the image-ID input set, both derived from the `COPY`
  instructions in the generated `Containerfile` so the helpers need no TOML
  parsing and there is no second list.
- Non-regular-file sources are rejected at generation time.
- Tests: editing a declared file changes the image ID; editing an undeclared
  file does not; a declared file reaches the build context and no
  execution-only file does.
- Design refs: [§7, §7.1](../design/container-config.md#7-image-identity).

### Commit 12: documentation

- Generated `.anvil/container/README.md` gains a section covering the
  configuration file, the four declaration kinds, when a change rebuilds the
  image, the trust model from
  [§3](../design/container-config.md#3-trust-model), and what the image tag
  does and does not guarantee.

## Phase 5 — Registered repository commands (WI 7689198)

### Commit 13: command dispatch

- Both drivers gain a first-argument check: a name matching a registered
  command selects command mode; otherwise the existing all-arguments-are-
  `anvil-*` rule applies unchanged. The generator's prefix ban makes the two
  modes unambiguous without a flag.
- Arguments are validated against their declared types, in order, with
  required-argument enforcement. `workdir` sets `--workdir` relative to
  `/workspace`. The recipe is invoked as `just <recipe> -- <args>`.
- A registered command is classified for GitHub-token acquisition by its
  resolved recipe and exposed to `customize.*` through the existing
  requested-recipes input.
- Unregistered names, argument-count mismatches, and type failures exit
  non-zero before any `docker` invocation.
- Driver tests on both hosts: successful dispatch with arguments; exit code and
  stdout/stderr propagation; each rejection path; each argument type accepted
  and rejected identically on both hosts; `anvil-*` recipes still work
  unchanged; a command cannot escape the worktree through `workdir` or a `path`
  argument.
- Design refs:
  [§5.4, §5.4.1](../design/container-config.md#54-containercommand-registered-repository-commands).

### Commit 14: trust documentation

- Generated README and design doc state plainly that registered commands are
  trusted repository code: they run inside the container with the worktree
  mounted read/write, and reviewing a branch that adds one is reviewing code
  that will run.
- Design refs: [§3, §5.4](../design/container-config.md#3-trust-model).

## Out of scope

- Development-container lifecycle commands (WI 7689202) and the VS Code Dev
  Container adapter (WI 7689200). Both consume this contract and are planned
  separately; the adapter reads the same generated `runtime.conf`
  ([§9](../design/container-config.md#9-runtime-data-and-driver-obligations)).
- Volume garbage collection. This plan applies labels so lifecycle commands can
  prune; it removes nothing.
- Generator-side policy letting a catalog restrict caches, mounts, or commands.
  The gap is documented in
  [§8.1](../design/container-config.md#81-what-a-catalog-cannot-yet-constrain);
  no consumer needs it yet.
- Any change to the `customize.*` contract, the update algorithm, drift
  detection, or opt-out semantics.
- CI container jobs, remote image publication, and Windows containers, which
  remain out of scope per
  [containers.md §10](../design/containers.md#10-requirements-controls-and-limitations).
