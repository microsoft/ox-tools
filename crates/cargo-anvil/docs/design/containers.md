# Containerized execution

Run commands in a Linux image built from the repository's toolchain and tool
pins:

```console
just anvil-container just anvil-pr
just anvil-container cargo build
just anvil-container
```

The last command opens an interactive shell. Container execution is opt-in per
invocation; other recipes and generated CI workflows continue to run natively.
The image helps reproduce Linux checks, not the entire CI environment.

See [local execution](./local.md) for the recipes it wraps,
[updates](./updates.md) for generated-file ownership, and
[extensibility](./extensibility.md) for downstream catalogs.

## 1. Prerequisites

The host needs Git, `just`, PowerShell Core (`pwsh`), and a running container
engine. Anvil installs none of these and manages no virtual machine.

The image installs tools through `just anvil-setup binstall`. A root
`rust-toolchain.toml` or `rust-toolchain` is honored when present; otherwise the
declared root MSRV selects the default compiler. The host's `RUSTUP_TOOLCHAIN`
is not inherited.

## 2. Commands and controls

| Recipe | Behavior |
| --- | --- |
| `just anvil-container <command…>` | Run a command; without arguments, open a shell. |
| `just anvil-container-tag` | Print the input-derived image reference without building. |
| `just anvil-container-status` | Report the engine, mount point, image reference, and local availability; never build or pull. An unreachable engine is reported as unknown. |
| `just anvil-container-down` | Remove this repository's Cargo cache volumes, retaining the image. |

Arguments are whitespace-delimited: an argument containing spaces does not
round-trip through the variadic recipe. Use the run-environment hook for such
values rather than command arguments.

| Environment variable | Effect |
| --- | --- |
| `ANVIL_CONTAINER_ENGINE` | Select `docker` (default) or `podman`. |
| `ANVIL_CONTAINER_NO_REBUILD=1` | Fail rather than build; the resolve hook may still fetch an image. |
| `ANVIL_CONTAINER_NO_RESOLVE=1` | Skip the image-resolution hook. |
| `ANVIL_CONTAINER_NO_CACHE=1` | Force a local build with `--no-cache`, skipping local reuse and the resolve hook. |
| `ANVIL_IN_CONTAINER=1` | Execute a nested command directly instead of starting another container. The image sets this automatically. A nested no-argument invocation fails. |

`NO_REBUILD` still prevents building when combined with `NO_CACHE`. Status
queries ignore `NO_CACHE` and disable both building and resolution.

Scope a forced rebuild to one invocation so later runs can reuse the image:

```powershell
$env:ANVIL_CONTAINER_NO_CACHE = '1'
try { just anvil-container cargo build }
finally { Remove-Item Env:ANVIL_CONTAINER_NO_CACHE }
```

## 3. Generated files and image contents

- `justfiles/anvil/container.just`: generated recipes.
- `.anvil/container/Dockerfile.dockerignore`: generated build-context filter.
- `.anvil/container/Dockerfile`: repository-owned file with five Anvil-managed
  regions. Add custom instructions in the gaps; regeneration preserves them.
- `.anvil/container/hooks.ps1`: optional repository or catalog hook, not
  generated by default.

The Dockerfile and its ignore file must keep these exact names. Keep the
`# syntax=docker/dockerfile:1` directive first and the managed regions in order.
Edits inside managed regions require reconciliation; use gaps for additions.

| Gap after region | Suitable additions |
| --- | --- |
| `anvil-container-base-image` | A second `ARG BASE_IMAGE=…` to override the base before `FROM`. Keep it digest-pinned. |
| `anvil-container-base` | Root certificates, proxies, or package mirrors needed before downloads. |
| `anvil-container-tools` | Libraries needed to compile catalog tools. |
| `anvil-container-setup` | Packages or configuration needed by repository checks at run time. |
| `anvil-container-entry` | Final Dockerfile overrides; preserve the launcher's environment and mount contract. |

The build context admits only `.anvil/container/`, `justfiles/anvil/`, root
toolchain files, and the root `Cargo.toml`. `.anvil-proposed` files are excluded.
The manifest supplies the MSRV and is removed after setup; workspace source is
mounted at run time, not built into the image.

Put certificates, installer scripts, and other files needed by custom `COPY`
instructions under `.anvil/container/`. They then participate in both the build
context and image identity. Do not store credentials there: this directory is
copied into the image.

## 4. Image identity and reuse

The reference is `anvil-<repo>:<16 hex characters>`. The tag is derived from:

- Every file under `.anvil/container/` and `justfiles/anvil/`, excluding
  `.anvil-proposed` files.
- Root `rust-toolchain.toml` and `rust-toolchain`, when present.
- The resolved root MSRV, not the full manifest.

Hook source is included; hook output and credentials are not. File paths,
contents, and modes contribute to identity. Tracked modes come from Git's
index; stage executable-bit changes before running. Untracked regular files
are accepted, using their executable bit on Unix and ordinary-file mode on
Windows. Symlinks in image inputs are refused. Recipe and declared text-input
line endings are normalized for hashing.

A run first reuses the local tag, then tries `Anvil-ResolveImage`, then builds.
Any recipe edit can change the tag, even if it does not affect tool installation.
Use `anvil-container-tag` to obtain the reference rather than duplicating the
hashing algorithm.

**The tag identifies build inputs, not verified image contents or a
bit-for-bit reproducible build.** System packages are not version-pinned, so
clean builds can differ as distribution archives change. Keep base overrides
digest-pinned. Fetched images require a trusted publisher; use immutable
registry tags and restricted push access.

## 5. Runtime, mounts, and environment

Without `Anvil-PrepareEnv`, each invocation creates one container and removes
it on exit, using the persistent download caches listed below. Prepared mode
instead uses two sequential disposable containers and invocation-scoped caches
removed on exit; see **Authenticated preparation, credential-free validation**.
The caller must run from inside the repository; its working directory is
mapped beneath `/workspace`.

| Host resource | Container path |
| --- | --- |
| Repository bind mount, writable | `/workspace` |
| Common Git directory, for supported redirected checkouts | `/anvil/gitdir` |
| `anvil-<repo>-cargo-registry` volume | `/usr/local/cargo/registry` |
| `anvil-<repo>-cargo-git` volume | `/usr/local/cargo/git` |

Linked worktrees and separate-Git-directory clones are supported when their
Git directory lies within the common directory. Redirected checkouts with
`core.worktree`, including typical submodules, are refused; run from the
superproject or an ordinary clone instead.

Tools and toolchains come from the image, not host Cargo or rustup directories.
`target/` remains on the repository bind mount; switching between native and
container builds can trigger recompilation.

Image names and non-prepared volume names use the sanitized repository
directory name. Without `Anvil-PrepareEnv`, checkouts with the same sanitized
name share download caches, so `anvil-container-down` can affect another
checkout. Prepared-mode caches are unique to each invocation.

Linux engines run as the invoking non-root user's UID/GID; engines reached
through WSL use the WSL user's IDs. Docker Desktop handles Windows/macOS
ownership mapping. Rootless Podman has additional limitations below.

Nonempty host values for `PR_TITLE`, `BASE_REF`, `GITHUB_BASE_REF`,
`SYSTEM_PULLREQUEST_TARGETBRANCH`, `ANVIL_IMPACT`, and `ANVIL_MIRI_JOBS` are
forwarded. Other variables require `Anvil-RunEnv`, except for the explicit
GitHub-token option.

`ANVIL_IMPACT_INPUT_DIR` is not forwarded. A nonempty override combined with
`ANVIL_IMPACT=consume` fails: unset it to use the container's default impact
location, or run natively to use the host directory.

### GitHub authentication

Supply a least-privilege `GITHUB_TOKEN` in the host environment, then place
`--github-token` immediately after the recipe name:

```console
just anvil-container --github-token just anvil-aprz
```

The flag also works with the interactive shell. Without it, the token is not
forwarded. A missing or blank token fails before engine or image resolution;
Anvil never acquires credentials from the host GitHub CLI.

`GITHUB_TOKEN` is reserved in `Anvil-RunEnv`: returning it without the flag
fails; with the flag, the supplied host token takes precedence.

## 6. Engines and host setup

Docker is supported; Podman is best-effort. Select Podman through the host
environment, not a `just` variable override:

```powershell
$env:ANVIL_CONTAINER_ENGINE = 'podman'
```

Anvil uses the selected executable on `PATH`. If it is absent on Windows,
Anvil probes the default WSL distribution and translates paths for that
engine. It never switches to the other engine automatically.

- **Docker Desktop on Windows/macOS:** start Desktop and make its CLI
  available on `PATH`.
- **Docker Engine on Linux:** install and start the engine; ensure your user
  can access it.
- **Docker Engine in WSL:** install and start Docker in the default
  distribution. Host `just` and `pwsh` remain on Windows. The repository must
  be accessible to the daemon.
- **Podman on Windows:** install the CLI, run `podman machine init` and
  `podman machine start`, then select it with the environment variable above.
- **Podman on Linux:** install it and select it through the same variable.

## 7. Hooks and credentials

The optional `.anvil/container/hooks.ps1` runs on the **host with your
permissions**. Only use hooks and recipes from trusted repositories.

| Optional function | Return contract |
| --- | --- |
| `Anvil-BuildSecrets` | `@{ Secrets = @{ id = value } }`, before building. |
| `Anvil-RunEnv` | `@{ Env = @{ NAME = value } }`, before running. |
| `Anvil-PrepareEnv` | Only `@{ Env = @{ NAME = value } }`, for fixed authenticated dependency preparation instead of runtime forwarding. |
| `Anvil-ResolveImage $tag` | A locally available image reference, or nothing, on a local cache miss. |

Omit a credential function when it is unnecessary. A defined function returning
no entries or a blank value fails the operation. Acquire short-lived
credentials when the function runs, not from committed files.

For example, forward a host-supplied registry token:

```powershell
function Anvil-RunEnv {
    @{ Env = @{ CARGO_REGISTRIES_INTERNAL_TOKEN = $env:CARGO_REGISTRIES_INTERNAL_TOKEN } }
}
```

Build secrets are exposed as `--secret id=<id>,env=ANVIL_SECRET_<id>`.
Consume them with required mounts in custom Dockerfile instructions:

```dockerfile
RUN --mount=type=secret,id=feed_token,required=true \
    TOKEN="$(cat /run/secrets/feed_token)" your-installer
```

Secret values and run-environment values are passed to the engine by name,
not embedded in process arguments. Build secret mounts do not become image
layers, but files written using them do: remove credential files in the same
`RUN` instruction that creates them.

### Authenticated preparation, credential-free validation

Use `Anvil-PrepareEnv` instead of `Anvil-RunEnv` when credentials are needed
only to download locked Cargo dependencies:

```powershell
function Anvil-PrepareEnv {
    @{ Env = @{ CARGO_REGISTRIES_INTERNAL_TOKEN = $env:CARGO_REGISTRIES_INTERNAL_TOKEN } }
}
```

Anvil runs exactly `cargo fetch --locked` in a disposable container with a
read-only checkout/history and fresh invocation-scoped registry/git caches.
The hook supplies environment only, not a command, file or mount. Every
returned value is sensitive; blank values and driver-control overrides are
rejected. Defining `Anvil-RunEnv` as well, or passing `--github-token`, fails
before acquiring preparation credentials.

Preparation output is captured rather than streamed. Any exact credential
value in either output stream or any cache-file bytes rejects preparation;
incomplete inspection also fails. Sensitive diagnostics are withheld. After
the preparation container is removed, only inspected registry/git caches
reach a **fresh** validation container. Its requested command runs with
`CARGO_NET_OFFLINE=true`, without the hook values, preparation home,
configuration, credential files or mounts. Containers and temporary cache
volumes are removed on success and failure; cleanup errors fail the run.
Every invocation prepares anew. Missing locked dependencies fail offline;
there is no retry with credentials or fallback to runtime authentication.

Preparation uses image-owned Cargo/rustc, disables compiler wrappers and
workspace host/compiler-backend flags, and neutralizes Cargo-forced native
loader settings. The image LLVM backend is selected with a preparation-only
`RUSTC_BOOTSTRAP=1`; neither bootstrap nor these compiler/loader overrides
reach validation or legacy runs. Source/authentication configuration remains
available. Hooks, the image and authentication providers must be trusted;
workspace compiler callbacks need not be trusted with the preparation values.

This mode is not a network or general execution sandbox. It does not intercept
independently supplied or renamed Cargo executables, restrict arbitrary
network clients, or make an untrusted hook safe. Without `Anvil-PrepareEnv`,
the existing runtime authentication behavior is unchanged.

### Resolving published images

The resolution hook may pull an image and return its reference:

```powershell
function Anvil-ResolveImage {
    param([string]$tag, [string]$Engine, [string[]]$EnginePrefix)
    $remote = "registry.example.com/anvil:$($tag.Split(':')[-1])"
    & $Engine @EnginePrefix pull $remote | Out-Null
    if ($LASTEXITCODE -eq 0) { $remote }
}
```

Declare both `Engine` and `EnginePrefix` to receive the selected engine command,
including WSL routing. Authenticate to the registry as required without putting
credentials in command arguments.

The returned reference is checked for local presence and used without
retagging. Runs use `--pull=never`; the hook must fetch the image itself.
Presence does not verify its contents.

Resolution errors fall through to a local build unless `NO_REBUILD` forbids it.
Build and run hook errors are fatal, including failure to load the script.
Anvil does not publish or promote images.

### Security boundary

This is not a sandbox for untrusted code. Commands can modify the mounted
repository and Git data. Everything executed inside the container, including
dependency build scripts and procedural macros, can read forwarded
runtime credentials in the legacy `Anvil-RunEnv`/`--github-token` mode.
Prepared mode keeps its credentials out of that validation container.
Keep the forwarded set narrow and use short-lived,
least-privilege tokens only with reviewed code.

## 8. Customization

Repositories customize Dockerfile gaps and hooks. A downstream catalog can
replace container artifacts for all its consumers:

- `dockerfile_base_image()` and `dockerfile_tools()` select a different base
  or tool-installation source.
- `hooks(…)` supplies the hook script.
- `dockerignore()` changes the admitted build context.
- `without_artifact` removes artifacts from the container group.

Preserve the setup and entry contracts when replacing regions. A base must
support the installed binaries; older glibc versions may not support catalog
tools' prebuilt binaries.

The hashed input set is fixed. Keep extra copied files under
`.anvil/container/`; widening the ignore file to admit another tree does not
add that tree to image identity. Otherwise changes there can silently reuse
an old image and require an explicit no-cache rebuild.

## 9. Limitations

- Build and run target `linux/amd64` only. ARM64 hosts require emulation and
  can be substantially slower; this does not validate native ARM behavior.
- A cold build installs the pinned tool catalog and can take several minutes.
  Recipe edits can require rebuilding.
- Command arguments containing whitespace are unsupported.
- Podman build secrets on Windows are unsupported; use Docker when build-time
  credentials are required.
- Rootless Podman does not receive `--userns keep-id`; bind-mount ownership
  may not map to the host user.
- The repository bind mount shares build output with native runs. The image
  does not isolate those artifacts or reproduce every CI-agent condition.
- Input-derived tags do not guarantee reproducible system packages or
  authenticate registry images.

## 10. Provisioned system-test suite

`scripts/test-anvil-container.ps1 -PreparationContractsOnly` executes the real
launcher template and extracted cache scanner with scripted engine/host
collaborators. It covers ordering, child-scoped credentials, rejection,
redaction, cleanup/status and bounded exact-byte scanning. It needs PowerShell
7 and its .NET APIs, the worktree template and temporary storage, but no engine,
Cargo build, just, service or credentials. Missing prerequisites fail; no cases
are silently skipped. Cargo's `test-util` artifact contracts and snapshots
prove emission in-process, not PowerShell execution.

Focused runs own a unique temporary directory and child environments. They
reject unscripted collaborator calls, preserve host environment and working
directory, and remove their exact fixtures in `finally`. The target budget is
two minutes, with a five-minute safety deadline and no retries; the scanner
probe reads a 256 MiB cache under a 128 MiB managed-heap cap.

The normal `-Engine docker` and `-Engine podman` modes run these contracts too,
then exercise genuine authenticated fetching and fresh offline compilation
with synthetic credentials. Only those real-engine cases prove actual mounts,
registry authentication and build-script/procedural-macro/test isolation.
They retain the Cargo/just/engine/default-network prerequisites and exclusively
own the existing fixture namespace; run them serially. Check invocation cleanup
before final fixture teardown. Budget roughly 50 minutes for Docker and
30 minutes for Podman on the supported worker. Relevant unchanged engine proof
can be retained after comparing product, fixture/oracle, toolchain/image and
environment inputs; relocating focused contracts alone does not require
repeating the full campaigns.
